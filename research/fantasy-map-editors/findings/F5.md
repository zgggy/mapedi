# F5: Export, interop and performance expectations

## Findings

### [1] Foundry VTT enforces a minimum scene grid of 50 px per square, defaults to 100 px, and documents 70/100/140/200 px as the common sizes maps are authored at.
- quote: "Foundry's default is 100 pixel squares, and has a minimum of 50px squares. Most maps use grid sizes of 70, 100, 140, or 200 pixels per square."
- url: https://foundryvtt.com/article/scenes/
- source_type: primary
- published: unknown (article current as of 2026 fetch; footer © 2026)
- confidence: high

### [2] Foundry scene pixel dimensions are auto-derived from the background image but can be overridden; changing dimensions auto-repositions tokens/tiles/walls, and padding is a percentage of scene size used as unlit staging space.
- quote: "This allows you to set the the rendered width and height of your scene in pixels. The application will figure out both automatically when you select a new scene background image, but you can override these dimensions using the fields provided."
- url: https://foundryvtt.com/article/scenes/
- source_type: primary
- published: unknown
- confidence: high

### [3] Foundry scene-level interop is JSON document export/import (Export Data / Import Data on the Scenes sidebar), not a GIS or vector format — a full Scene Document dump that overwrites the target scene.
- quote: "You can export an scene's data by right-clicking a scene in the Directory and selecting the \"Export Data\" option. This will prompt you to save a JSON file with the scene data in it."
- url: https://foundryvtt.com/article/scenes/
- source_type: primary
- published: unknown
- confidence: high

### [4] Foundry offers Preload Scene so connected clients can fetch image/video assets in the background before activation — the documented mitigation for large scene load times in multiplayer VTT use.
- quote: "Preload Scene ( ) Request that all connected Users begin loading the image and video assets needed to display this Scene in the background."
- url: https://foundryvtt.com/article/scenes/
- source_type: primary
- published: unknown
- confidence: high

### [5] RFC 7946 GeoJSON locks all coordinates to WGS 84 lon/lat in decimal degrees (optional height as 3rd element) and forbids alternate CRS members, so fantasy-map GIS export must either use a spherical CRS or stay outside strict GeoJSON.
- quote: "The coordinate reference system for all GeoJSON coordinates is a geographic coordinate reference system, using the World Geodetic System 1984 (WGS 84) datum, with longitude and latitude units of decimal degrees."
- url: https://www.rfc-editor.org/rfc/rfc7946.html
- source_type: primary
- published: 2016-08
- confidence: high

### [6] GeoJSON geometry vocabulary is a fixed set of seven types (Point, MultiPoint, LineString, MultiLineString, Polygon, MultiPolygon, GeometryCollection) plus Feature/FeatureCollection; types MUST NOT be extended, so semantic layers (height/environment/culture/religion/country/province) must ride in Feature.properties or foreign members.
- quote: "Implementations MUST NOT extend the fixed set of GeoJSON types: FeatureCollection, Feature, Point, LineString, MultiPoint, Polygon, MultiLineString, MultiPolygon, and GeometryCollection."
- url: https://www.rfc-editor.org/rfc/rfc7946.html
- source_type: primary
- published: 2016-08
- confidence: high

### [7] GeoJSON coordinate precision is the dominant payload-size lever: 6 decimal places (~10 cm) is recommended; going to 15 decimals can nearly double a detailed Polygon-heavy file.
- quote: "A GeoJSON text containing many detailed Polygons can be inflated almost by a factor of two by increasing coordinate precision from 6 to 15 decimal places. For geographic coordinates with units of degrees, 6 decimal amounts to about 10 centimeters"
- url: https://www.rfc-editor.org/rfc/rfc7946.html
- source_type: primary
- published: 2016-08
- confidence: high

### [8] GeoJSON requires antimeridian cutting for geometries that cross ±180° (as MultiLineString/MultiPolygon), a concrete rule Mapedi's spherical world must honor for globe-adjacent export correctness.
- quote: "Any geometry that crosses the antimeridian SHOULD be represented by cutting it in two such that neither part's representation crosses the antimeridian."
- url: https://www.rfc-editor.org/rfc/rfc7946.html
- source_type: primary
- published: 2016-08
- confidence: high

### [9] GeoJSON allows \"foreign members\" for extensions but warns they have no normative processing model and reduce interoperability — the standard escape hatch for fantasy-specific attributes without breaking GIS tooling.
- quote: "Members not described in this specification (\"foreign members\") MAY be used in a GeoJSON document. Note that support for foreign members can vary across implementations, and no normative processing model for foreign members is defined."
- url: https://www.rfc-editor.org/rfc/rfc7946.html
- source_type: primary
- published: 2016-08
- confidence: high

### [10] SVG 1.1 length units include physical print units (em, ex, px, pt, pc, cm, mm, in), so vector map export can carry true print size independent of screen pixel density.
- quote: "The supported length unit identifiers are: em, ex, px, pt, pc, cm, mm, in, and percentages."
- url: https://www.w3.org/TR/SVG11/coords.html
- source_type: primary
- published: 2011-08-16 (SVG 1.1 Second Edition)
- confidence: high

### [11] SVG viewBox maps a user-space rectangle onto the viewport so one vector map can scale to arbitrary raster resolutions (print DPI or screen px) without re-export; zero width/height disables rendering and negative values are an error.
- quote: "The value of the ‘viewBox’ attribute is a list of four numbers <min-x>, <min-y>, <width> and <height>... which specify a rectangle in user space which should be mapped to the bounds of the viewport established by the given element"
- url: https://www.w3.org/TR/SVG11/coords.html
- source_type: primary
- published: 2011-08-16
- confidence: high

### [12] OGC Two Dimensional Tile Matrix Set v2.0 (17-083r4) is the formal web-tile index: each tile is identified by (tile matrix id, tile column, tile row) over a limited list of scales in a CRS, with XML and JSON encodings and consumers WMTS, OGC API – Tiles, and GeoPackage.
- quote: "In a tile matrix set, a tile can be univocally identified by a tile column, a tile row, and a tile matrix identifier."
- url: https://www.ogc.org/standard/tms/
- source_type: primary
- published: unknown (standard v2.0 doc 17-083r4; site fetched 2026-09)
- confidence: high

### [13] W3C Media Fragments URI defines a portable spatial crop syntax (xywh=pixel:x,y,w,h or percent:x,y,w,h) applicable to images, useful for deep-linking map regions without shipping a full tile pyramid.
- quote: "Rectangle selection is denoted by the name `xywh`. The value is an optional format `pixel:` or `percent:` (defaulting to pixel) and 4 comma-separated integers."
- url: https://www.w3.org/TR/media-frags/
- source_type: primary
- published: 2012-09-25 (W3C Recommendation)
- confidence: medium (standard is real and precise; adoption in map editors is unverified here)
